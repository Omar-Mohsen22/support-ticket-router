# ticket-router

This project routes customer-support tickets. Each ticket gets three labels: `queue` (10
classes), `priority` (3) and `type` (4). I solved the task three ways: TF-IDF features with
logistic regression, zero-shot `gpt-4o-mini`, and `Qwen/Qwen2.5-1.5B-Instruct` fine-tuned with
QLoRA. A random baseline sets the floor. Every run is scored by the same harness
(`src/ticket_router/evaluate.py`) on the same frozen test split of 1,633 tickets
(`data/processed/test.parquet`, committed). `evaluate.py` hashes the ordered test ids and refuses
to save a run scored against a different split.

### Notes

`[cost_basis]` next to a 0 cost, and `[hardware]` next to every latency figure, are generated from each run's `results/<run-name>.run_meta.json` -- not hand-typed.

**What a `[cost_basis]` tag means:**

- `api-per-token`: a hosted API call. The provider doesn't return a live $ figure per request, so a cost_usd of 0 here means UNMEASURED -- compute a real figure externally from the recorded input/output token counts -- not that the call was free.
- `cpu-local`: runs entirely on a local CPU. A cost_usd of 0 here is real and measured -- genuinely free to run, no ambiguity.
- `gpu-local`: a self-hosted model that requires a GPU to serve. A cost_usd of 0 here is NOT "free" -- this harness tracks no $/GPU-hour serving rate. See that run's training_cost for what training it actually cost.

**Training cost** (a one-time cost, not part of any single prediction above -- so it is not, and cannot be, folded into `latency_ms` or `cost_usd`):

- `qlora-adapter-ckpt1500`: 3.35 GPU-hour(s). 3.35 GPU-hour(s) on Tesla T4 (Google Colab, free tier) to train this adapter (hub_model_id in train/config.yaml). The $0 training cost is because the free tier absorbed it, not because training itself was free -- and this is a one-time cost, separate from what serving each prediction below costs.

Runs not listed above required no GPU training step of their own -- either a pre-trained hosted API model, or (TF-IDF, the random baseline) a fit measured in seconds of CPU time, not GPU-hours; see each such run's `training_cost.note` in `results/results.json` for the exact figure.

## What the results say

- **The fine-tune beats zero-shot `gpt-4o-mini` on every field.** Queue 0.3999 vs 0.2554,
  priority 0.4944 vs 0.3214, type 0.8559 vs 0.5209. Exact match 26.03% vs 10.90%.
- **Against TF-IDF it is a split decision.** The fine-tune wins queue (0.3999 vs 0.3683) and
  type (0.8559 vs 0.8412). It loses priority (0.4944 vs 0.5445) and exact match (26.03% vs
  29.33%). TF-IDF trains in 3.06 s on a CPU. The adapter took 3.35 GPU-hours.
- **Few-shot prompting did not close the gap.** Three few-shot variants of `gpt-4o-mini` are
  in the full table above. None of them reached TF-IDF on any field. Details are in
  `reports/prompting_notes.md`.
- **`priority = low` (345 test tickets).** Zero-shot `gpt-4o-mini` and two of the three
  few-shot variants scored 0 recall. The third few-shot variant scored 0.0058 (2 of 345). The
  fine-tuned adapter scored 0.2783, the highest of any run. That is above `tfidf-baseline`
  (0.2406) and `random-baseline` (0.1855).

## Error analysis

Full report: [`reports/error_analysis.md`](reports/error_analysis.md), generated by
`src/ticket_router/error_analysis.py`. It compares the fine-tuned adapter with TF-IDF ticket by
ticket. The two models are architecturally unrelated: bag-of-words features with a linear
classifier, versus a fine-tuned transformer.

**They fail on largely the same tickets, and usually pick the same wrong label.**

| field | rows where at least one model is wrong | both wrong | both wrong, same wrong label |
| --- | --- | --- | --- |
| queue | 986 | 653 (66.2%) | 471 (72.1% of both-wrong) |
| priority | 981 | 444 (45.3%) | 341 (76.8% of both-wrong) |
| type | 323 | 157 (48.6%) | 157 (100% of both-wrong) |

**Caveat on `type`.** Treat the 100% figure on its own as weak evidence, because it is close to
forced. Almost all `type` errors are Problem <-> Incident: 231 of the adapter's 234 errors
(98.7%) and 237 of TF-IDF's 246 (96.3%). When both models are wrong on a ticket, there is
almost only one wrong label left to pick.

**Both models over-predict Technical Support.** The test set has 474 gold Technical Support
tickets. The adapter predicts Technical Support 858 times and TF-IDF 869 times. These are the
column sums of the confusion matrices in the report.

**IT Support is mostly absorbed into Technical Support.** Of 194 gold IT Support tickets, the
adapter sends 139 (71.6%) to Technical Support. TF-IDF sends 112 (57.7%).

**The stronger evidence is in the sampled tickets.** The report prints 10 misclassified
tickets per field, chosen to cover the most-confused label pairs. In several of them the
ticket text contradicts the gold label:

- `tkt_011979`, gold `priority = low`: "We are currently facing critical issues with the
  hospital's system, where we have identified potential data security vulnerabilities..."
  (adapter: `medium`, TF-IDF: `high`)
- `tkt_023949`, gold `queue = Billing and Payments`: "A healthcare provider faced unauthorized
  access attempts to medical data." (both models: `Technical Support`)
- `tkt_024807`, gold `queue = Billing and Payments`: "Would you be able to provide details on
  how data analytics can enhance investment strategies for financial firms?" (both models:
  `Customer Service`)

**Conclusion.** Two unrelated models share the same plateau, and samples like these exist. Both
suggest that the remaining errors are largely a property of the labels, not of either model.
That is why I did not pursue further tuning. It does not mean all errors are label noise. On
`queue`, exactly one of the two models is right on 333 tickets (150 adapter-only, 183
TF-IDF-only). Those errors are model-specific.

## Training details

- **Base model:** `Qwen/Qwen2.5-1.5B-Instruct` (`train/config.yaml`). An open-weights model
  was chosen over fine-tuning a hosted API model so that the result can be self-hosted and
  compared on cost against the API.
- **QLoRA:** 4-bit NF4 quantization with double quantization. LoRA r=16, alpha=32, dropout
  0.05, on `q_proj`, `k_proj`, `v_proj`, `o_proj`, `gate_proj`, `up_proj`, `down_proj`.
- **Loss:** on completion tokens only. The data is stored in TRL's prompt-completion format.
- **Schedule:** 3 epochs over 13,070 training examples. Effective batch size 16 (4 per device
  x 4 gradient accumulation). Learning rate 2e-4, cosine schedule, warmup ratio 0.03,
  `paged_adamw_8bit`, max sequence length 384. The run ended at step 2451.
- **Hardware:** one Tesla T4 on Google Colab (free tier), 3.35 GPU-hours.
- **Notebook:** [`notebooks/train_qlora.ipynb`](notebooks/train_qlora.ipynb). It reads every
  setting from `train/config.yaml`.

**Checkpoint selection.** A checkpoint was saved every 250 steps. During training, eval loss
was tracked on a fixed 400-example subsample of the validation set, for monitoring only. After
training, all 10 checkpoints were scored on the full validation set (1,635 examples).
Checkpoint-1500 had the lowest loss and was selected. The final checkpoint (2451) was 7.24%
worse.

## Reproduce

Run everything from the repo root, with the virtual environment active.

```
python -m venv .venv
# Windows: .venv\Scripts\activate    POSIX: source .venv/bin/activate
pip install -r requirements.txt
# copy .env.example to .env and fill it in:
# OPENAI_API_KEY for the API predictor, HF_TOKEN for the adapter predictor
```

1. Data. `test.parquet` and `val.parquet` are committed. `make_dataset.py` regenerates them
   identically, and also builds `train.parquet`, which the baselines and the fine-tune need.
   ```
   python src/ticket_router/inspect_data.py      # downloads the raw CSVs into data/raw/
   python src/ticket_router/make_dataset.py
   ```
2. Baselines. `tfidf_baseline.py` also overwrites the committed `models/tfidf/` artifact. A
   refit on another platform is not bit-identical (see Serving), so do not commit it casually.
   ```
   python src/ticket_router/predict_random_baseline.py
   python src/ticket_router/evaluate.py --predictions results/random-baseline.predictions.jsonl --split test --run-name random-baseline
   python src/ticket_router/predictors/tfidf_baseline.py
   python src/ticket_router/evaluate.py --predictions results/tfidf-baseline.predictions.jsonl --split test --run-name tfidf-baseline
   ```
3. Zero-shot `gpt-4o-mini`. Few-shot variants use `--variant coverage`,
   `coverage-priority` or `coverage-median`.
   ```
   python src/ticket_router/predictors/api_predictor.py --split test --run-name api-gpt4o-mini-full-test
   python src/ticket_router/evaluate.py --predictions results/api-gpt4o-mini-full-test.predictions.jsonl --split test --run-name api-gpt4o-mini-full-test
   ```
4. Fine-tune. Build the SFT files, then run `notebooks/train_qlora.ipynb` on a GPU (Colab).
   ```
   python src/ticket_router/make_sft_dataset.py
   ```
5. Score the adapter. This needs a CUDA GPU and `HF_TOKEN`.
   ```
   python src/ticket_router/predictors/adapter_predictor.py --split test --run-name qlora-adapter-ckpt1500
   python src/ticket_router/evaluate.py --predictions results/qlora-adapter-ckpt1500.predictions.jsonl --split test --run-name qlora-adapter-ckpt1500
   ```
6. Reports and tests.
   ```
   python src/ticket_router/report.py            # rebuilds results/comparison.md and both tables in this README
   python src/ticket_router/error_analysis.py    # rebuilds reports/error_analysis.md
   python -m pytest -q
   ```

## Serving

A FastAPI app serves the TF-IDF model (`src/ticket_router/api/app.py`). The adapter is not
served yet.

The served model is the committed artifact `models/tfidf/model.joblib`. It is the exact model
behind the published `tfidf-baseline` numbers: it reproduces all 1,633 test predictions, and its
sha256 is recorded in `models/tfidf/meta.json`. It is not refitted for serving, because a refit on
another platform is not bit-identical. A Linux refit on the same data changes some test
predictions; CI measures by how much (see below).

1. Start the server. It loads the artifact once at startup, and refuses to start if the
   artifact is missing.
   ```
   python -m uvicorn ticket_router.api.app:app --app-dir src --port 8000
   ```
2. Send a request. `subject` is optional; a missing, empty or blank subject means the body is
   used alone, as in training. An empty `body` returns 422.
   ```
   curl -X POST localhost:8000/predict -H "Content-Type: application/json"      -d '{"subject": "System Failure Caused by Overload", "body": "The investment optimization system encountered a crash, which may be due to data overload or a software bug. After rebooting and reviewing logs, the issue still persists. We need your assistance to resolve this problem."}'
   ```
   The response has `queue`, `priority`, `type`, `model` and `latency_ms`. `GET /health`
   reports whether the model is loaded.

**With Docker.** At build time, the image does three things:
- verifies the committed artifact against the sha256 in `meta.json`;
- downloads the dataset at a pinned Hub revision and rebuilds the splits;
- checks that the rebuilt test split is the one every published result used.

The build fails if either check fails. The image serves on port 7860, which is the Hugging Face
Docker Space default; set `PORT` to override.
```
docker build -t ticket-router .
docker run --rm -e CI=true ticket-router python -m pytest -q -rs -p no:cacheprovider
docker run --rm -p 7860:7860 ticket-router
curl localhost:7860/health
```

CI (`.github/workflows/ci.yml`) runs two jobs:
- **`docker`** runs the same build, runs the tests inside the image, then starts the container
  and checks `/health` and `/predict`.
- **`refit-sensitivity`** refits TF-IDF on Linux and scores it with the same metric code. The
  result goes to the job summary only; nothing published is changed.

**Hosted deployment (private for now).** The API runs on a private Hugging Face Docker Space,
[`Omar-Mohsen22/support-ticket-router`](https://huggingface.co/spaces/Omar-Mohsen22/support-ticket-router),
on free `cpu-basic` hardware (`https://omar-mohsen22-support-ticket-router.hf.space`). Requests
need an `Authorization: Bearer <HF token>` header with read access to the Space. On every push
to `master` whose `docker` job passes, the `deploy` CI job does the following
(`deploy/space/deploy_space.py`):
1. uploads exactly the files the Docker build needs;
2. waits for the Space to rebuild and reach `RUNNING`;
3. smoke-tests `/health`, and `/predict` on a real test ticket, whose output must match the
   published prediction.

Measured in the first deploy (CI run `36261663632`), from a GitHub-hosted runner, so the times
include the network round trip:
- first `/health` after the rebuild: 250 ms;
- first `/predict`: 196 ms;
- warm `/predict`: median 211 ms over 5 requests;
- the server's own `latency_ms` for those requests: 3.3-6.8 ms.

A cold start after the Space goes to sleep was not measured.

The API builds its input with the same `build_ticket_text()` that built the training data
(`src/ticket_router/ticket_text.py`). A parity test in `tests/test_api.py` checks that the API
reproduces `results/tfidf-baseline.predictions.jsonl` exactly, on all 1,633 test tickets.

## Demo

I run a side-by-side demo on a Hugging Face ZeroGPU Space,
[`Omar-Mohsen22/support-ticket-router-demo`](https://huggingface.co/spaces/Omar-Mohsen22/support-ticket-router-demo)
(private for now).
- **TF-IDF** runs on the CPU.
- **My QLoRA adapter** runs on a shared GPU, with the same inference config as the evaluated
  run: 4-bit NF4 base, adapter not merged, float16 compute, greedy decoding. It is loaded through
  the same `load_model_and_tokenizer()` as `src/ticket_router/predictors/adapter_predictor.py`.

**It reproduces the evaluated model's predictions.** I ran all 1,633 test tickets through the deployed demo,
in batches of 8 as in the evaluated run:
- It matched the published adapter predictions on **1,623 / 1,633 (99.39%)** on all three
  fields.
- Its macro-F1 is within 0.003 of the published numbers on every field.
- Its one invalid output is the same ticket as in the published run (`tkt_003783`).

Full numbers: [`reports/adapter_zerogpu_4bit_full.md`](reports/adapter_zerogpu_4bit_full.md).
The headline tables above stay the published evaluation.

**An earlier setup did not reproduce it.** My first demo loaded the base unquantized in
bfloat16, merged the adapter and ran batches of 16. It agreed with the published predictions on
only 72.6% of tickets and scored lower on every field
([`reports/adapter_zerogpu_agreement.md`](reports/adapter_zerogpu_agreement.md)). The hardware
is not the cause: the evaluated 4-bit config on ZeroGPU (Blackwell) matched the T4 run. So the
gap comes from precision, merging, batch size, or a mix of these; I did not isolate which.

**Latency.** 4-bit quantization needs a real GPU, and ZeroGPU only attaches one inside a request.
So the model is loaded on every request (about 1.7-2.4 s), and an answer takes a few seconds.
The page sends one ticket at a time, so there is no batch padding; a single-ticket answer can occasionally differ from the batched results above.

## Limitations

- **English only.** 16,338 of the 28,587 rows in the source file are English, and only those
  are used (`data/README.md`).
- **Synthetic data.** Per `data/README.md`, the tickets are synthetic (LLM-generated), not
  real customer correspondence. Results may not transfer to real tickets.
- **One training run, one seed** (`seed: 42`). There are no repeated runs and no confidence
  intervals. Small gaps, such as type F1 0.8559 vs 0.8412, may not survive a re-run.
- **Refitting TF-IDF on different hardware changes some predictions.** Two CI runs refitted
  the baseline on Linux. 0 and 81 of 1633 test rows changed, and
  macro-F1 moved by at most 0.0027 on any field. The adapter-vs-TF-IDF ordering was
  unchanged on every field. Two runs are not enough to call this an error margin. The served
  artifact is the exact evaluated model; CI verifies it on all 1633 test rows.
- **Adapter weights are private for now.** They are hosted in a private Hugging Face repo,
  `Omar-Mohsen22/ticket-router-qwen2.5-1.5b-qlora`, so step 5 of Reproduce needs access to it.
- **Serving is private for now.** CI deploys the TF-IDF API to a private Hugging Face Space (see
  Serving). The adapter is served only in the private ZeroGPU demo (see Demo), not as an API.

## How I built this

I planned each step with Claude, made the decisions, and reviewed every plan and output before
it ran or was committed. Claude Code wrote most of the code. Commits are authored by me because I
made and reviewed every change. I disclose the AI assistance here, once for the whole project,
instead of in each commit. [CLAUDE.md](CLAUDE.md) holds the working rules I gave the assistant.

The main decisions, each recorded as a step in [PROGRESS.md](PROGRESS.md):

- **Data.** I used the Tobi-Bueck/customer-support-tickets dataset, and only one of its three
  files, filtered to English. The German-only file has a different queue taxonomy, and the third
  file might overlap with the chosen one and leak tickets across splits (steps 01-02).
- **One evaluation for three models.** gpt-4o-mini, TF-IDF and the fine-tuned adapter are scored
  by the same harness on the same 1,633-ticket test split (steps 03 and 15). I capped the
  few-shot prompting at a fixed set of variants (step 05). I decided how to report cost and
  latency before the fine-tuned model produced any numbers, so the result could not shape the
  framing (step 16). The harness also hashes the test split and fails loudly if a run was scored
  on a different one (step 17).
- **Stopping training.** The error analysis showed that the fine-tuned model and TF-IDF fail on
  the same tickets and usually pick the same wrong label. That points at the labels, not at
  model capacity. I decided to stop training at that point (step 19; the decision was recorded
  in step 31).
- **Deployment.** I tried other hosts first and chose Hugging Face PRO for the API and the demo
  (step 28). The demo first ran the adapter in bf16 with the adapter merged. Over all 1,633 test
  tickets it agreed with the published predictions on only 72.63%. The evaluated 4-bit config
  agreed on 399 of 400, so I switched the demo to it, and a full run then agreed on 1,623 of
  1,633 (step 29). The demo shows gpt-4o-mini's stored outputs instead of calling it live, so
  that visitors' requests are not billed to my API key (steps 29-30).
- **UI.** The demo page follows a design I approved, "Option A" (step 30).
- **Token rotation.** A scratch diagnostic script sent my Space deploy token to Google's font
  servers. I rotated the token, deleted the old one, and kept a rule: tokens are attached only to
  `*.hf.space` and `huggingface.co` requests (steps 30-31).
